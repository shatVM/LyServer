# LyServer — постійний контекст проєкту

> Призначення: коротко відновити контекст після перерви, у новому чаті або для іншого ШІ-агента. Це живий документ; перевіряйте його актуальність перед змінами.

## 1. Мета

LyServer («Навчальний простір») — локальний вебпортал навчальних матеріалів для використання в класі або укритті, зокрема коли зовнішній інтернет недоступний. Учительський комп'ютер/телефон і пристрої учнів працюють у спільній локальній мережі.

## 2. Підтверджений стан репозиторію

- Репозиторій: https://github.com/shatVM/LyServer
- Основна гілка: `clean-main`.
- На момент створення цього документа корінь містить `server.js`, `src/`, `views/`, `public/`, `package.json` і `README.md`.
- Точка входу `server.js` підключає `src/app` та `src/config`.
- У `package.json` визначено `npm start` як `node server.js`. Залежності включають Express, Handlebars, WebSocket (`ws`), а також засоби роботи з PDF/Canvas.
- README описує розділи матеріалів, завантаження та демонстрації, а також спільний стан демонстрації й індивідуальний перегляд. Перед будь-якою реалізацією треба перевірити, що опис відповідає поточному коду.
- Не вважати опис README доказом того, що кожна функція повністю протестована або працює без помилок.

## 3. Робоче середовище й мережа

- Основний локальний клон користувача: `C:\Users\Admin\Documents\LyServer`.
- Очікуваний Git remote: `https://github.com/shatVM/LyServer.git`.
- Відомий локальний сервер: `192.168.1.140:3000` — адреса з робочого контексту користувача. У репозиторії в окремих місцях можуть бути інші адреси; не замінювати їх масово без перевірки конфігурації та явного завдання.
- Середовище призначене для локальної мережі без обов'язкового доступу до інтернету. Хмарні тести не повинні залежати від фізичного роутера або реальної локальної мережі.

## 4. Поточні напрямки розвитку

1. Синхронна демонстрація для класу та окремий індивідуальний перегляд матеріалів.
2. Автоматичне перемикання учнів на внутрішню вкладку «Демонстрація», коли вчитель починає показ, із відновленням стану після підключення/перепідключення.
3. Присутність учнів і коректне відображення станів підключення.
4. Інтерактивні опитування, а згодом тести та результати.
5. Автоматизоване E2E-тестування з окремими сесіями вчителя й кількох учнів.
6. Надійний запуск і робота сервера в офлайн-локальній мережі.
7. Автоматизація GitHub → OpenCode з ізольованими завданнями, гілками та перевіркою результатів.

Це перелік напрямків, а не твердження, що вони вже реалізовані.

## 5. GitHub: відомі Issues

- Issue #1 — [План розвитку: автоматизоване тестування, присутність учнів та інтерактивні опитування](https://github.com/shatVM/LyServer/issues/1). Це загальний roadmap із кількома етапами; не слід доручати агенту реалізувати його цілком за один запуск.
- Issue #1 також містить вимогу автоматично перемикати підключені учнівські клієнти на внутрішню вкладку «Демонстрація» після початку показу вчителем, а також відновлювати стан для нових/повторно підключених учнів.
- Issue #2 — [ТЕСТ: валідація диспетчера OpenCode](https://github.com/shatVM/LyServer/issues/2). Тестова задача, що вимагає лише прочитати стан Git-репозиторію; у ній прямо заборонені зміни коду, гілок і коміти.
- Відомі мітки для потоку диспетчера: `ready-for-opencode`, `in-progress`, `opencode-review`.

## 6. OpenCode / диспетчер — стан, який треба перевіряти

- У користувача встановлено OpenCode v2.0.27.
- Модель `opencode/mimo-v2.6-flash-free` використовувалася для успішного read-only тесту Issue #2 за попереднім звітом.
- Моделі `opencode/gemini-4-argon` і `opencode/claude-haiku-5-5` раніше повертали `Insufficient account funds`; не припускати, що вони доступні для запуску.
- Раніше був підготовлений початковий read-only PowerShell-диспетчер v0.1, але його наявність у репозиторії та актуальний шлях необхідно перевірити.
- Диспетчер v0.2 із логами, попередніми перевірками, перевіркою результатів/GitHub і без автоматичного злиття був погоджений як задум, але факт створення та перевірки такого файлу не підтверджений.
- Перед продовженням попросити/прочитати останній звіт агента про диспетчер і звірити його з файлами та станом GitHub. Не вигадувати, що диспетчер уже виконує завдання, створює PR або пройшов повний тест.

## 7. Як відновлювати контекст

На початку нового сеансу:
1. Прочитати `AGENTS.md`, цей файл, `REQUIREMENTS.md` і `DECISIONS.md`.
2. Перевірити гілку, `git status`, останні коміти, актуальні Issue/PR та наявні тести.
3. Звірити факти, що могли змінитися, з кодом і повідомленнями власника.
4. Після істотних змін оновити документи та зазначити це у звіті.

Останнє оновлення: початкове створення документації пам'яті проєкту. Дату й стан уточнювати під час наступного змістовного оновлення.
