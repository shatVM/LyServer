# Процес поетапної роботи над GitHub Issue

Цей документ визначає порядок спільної роботи власника проєкту та агента-розробника (Dev-агента) над великими завданнями LyServer. Мета — зберігати повні вимоги, виконувати роботу контрольованими етапами, документувати результати та не переходити до наступного етапу без погодження.

## 1. Джерела вимог

Для кожного завдання, яке виконується поетапно, використовуються:

1. **Основний текст GitHub Issue** — повна специфікація: функціональні вимоги, обмеження, вимоги до інтерфейсу, безпеки та критерії приймання. Його не замінюють короткими описами етапів.
2. **Коментарі до Issue** — окремі завдання на кожен етап. Кожен коментар визначає мету, межі роботи, дозволені дії, заборони, формат звіту та критерії завершення.
3. **Звіт Dev-агента** — короткий звіт про виконання етапу, який можна залишити звичайним коментарем у відповідній Issue або PR.
4. **Погодження власника проєкту** — обов’язкова умова для переходу до наступного етапу, початку реалізації після аудиту або злиття запиту на злиття (pull request, PR).

Якщо коментар етапу суперечить основному Issue, агент не повинен самостійно обирати один із варіантів. Він має описати суперечність у звіті й попросити власника уточнити вимоги. Основний Issue визначає загальні вимоги, а коментар — обсяг поточного етапу.

## 2. Мовні вимоги

**Українська мова є основною мовою проєкту для інтерфейсу, документації та робочої комунікації.** Dev-агент має дотримуватися таких правил:

- Усі нові або змінювані тексти інтерфейсу, повідомлення, підказки, назви кнопок, помилки, підтвердження дій та інші тексти для користувачів писати українською мовою.
- Документацію проєкту, README, описи завдань і запитів на злиття, коментарі до етапів та звіти виконання писати українською мовою.
- Спілкуватися з власником проєкту українською мовою, зокрема пояснювати результати перевірок, ризики та невирішені питання.
- Не перекладати й не перейменовувати без потреби технічні ідентифікатори, назви бібліотек, API, команд, файлів, змінних, функцій, маршрутів і параметрів, якщо це може порушити сумісність або суперечить усталеним технічним правилам.
- Англомовні назви технологій, стандартів і загальноприйняті технічні терміни дозволені там, де переклад погіршив би точність. За першої згадки незнайомого терміна бажано коротко пояснити його українською.
- Якщо в межах завдання виявлено наявні англомовні користувацькі тексти, не змінювати їх масово поза погодженим обсягом. Зазначити їх у звіті й запропонувати окреме рішення, якщо це потрібно.
- Перед завершенням етапу перевірити, чи всі додані або змінені тексти відповідають цим мовним вимогам.

## 2.1. Інтерактивна взаємодія Tech-lead із власником

У чаті Tech-lead має віддавати перевагу справжнім інтерактивним елементам вибору (radio/select/checkbox/кнопки), коли власнику потрібно обрати варіант, наступний крок або статус. Не проси власника вручну друкувати назву варіанта, номер чи команду, якщо це можна подати інтерактивно. Елемент має бути підключений до реальної дії/наступного кроку, а не бути декоративним.

Якщо потрібен один критично важливий факт і форма не спрощує взаємодію, постав одне коротке пряме запитання. Не створюй довгу форму для широкого або дослідницького завдання. Якщо власник просить виконати роботу й даних достатньо, виконуй її, а не перекладай на нього ручне введення команд чи тексту.

GitHub-коментарі не підтримують інтерактивні елементи чату. У завданнях і звітах на GitHub використовуй зрозумілий Markdown, чіткі межі та критерії; інтерактивний вибір власника показуй у чаті, де це доступно.

## 3. Робочий цикл

1. Власник створює коментар із номером етапу та чіткими межами роботи.
2. Власник передає Dev-агенту посилання на основний Issue і на конкретний коментар поточного етапу.
3. До виконання будь-яких дій агент перевіряє поточний стан Git: гілку, HEAD, стан робочого дерева та незбережені зміни.
4. Агент виконує лише погоджений етап.
5. Якщо потрібен звіт на GitHub, агент може опублікувати один звичайний коментар у відповідній Issue або PR. Перший рядок — `Dev-agent`. Не створюй додаткових коментарів лише заради формату звіту.
6. Власник перевіряє звіт разом із помічником або рецензентом і явно погоджує наступний етап чи повертає роботу на доопрацювання.
7. Наступний етап починається лише після явного погодження. Мовчання, завершення попереднього етапу або автоматичне повідомлення не є дозволом продовжувати.
8. Для етапів реалізації використовувати окрему гілку, запускати доречні перевірки й відкривати PR до гілки `clean-main`. **Не зливати PR без окремого підтвердження власника.**

### Чому потрібно вказувати конкретний коментар

Не використовувати неоднозначні вказівки на кшталт «виконай останній коментар»: згодом можуть з’явитися уточнення або коментарі інших учасників. Завжди передавати URL або номер коментаря, який визначає завдання поточного етапу.

### Обов’язковий префікс коментаря

- Коментар ChatGPT у ролі технічного керівника починається з окремого першого рядка `Tech-lead`.
- Коментар Dev-агента починається з окремого першого рядка `Dev-agent`.
- Це правило діє для всіх нових коментарів у GitHub Issues і Pull Requests, зокрема звітів, уточнень і повідомлень про виконання.

## 4. Універсальна інструкція для Dev-агента

Для кожного етапу скопіювати наведену нижче інструкцію, підставивши посилання на Issue та конкретний коментар:

> Працюй із репозиторієм `shatVM/LyServer`.
>
> **Основне технічне завдання:** [посилання на GitHub Issue]
>
> **Єдиний етап, який дозволено виконувати зараз:** [посилання на конкретний коментар Issue]
>
> Перед початком прочитай повний текст основного Issue, усі його вимоги й обмеження, а також конкретний коментар поточного етапу. Основний Issue є повною специфікацією, а коментар визначає межі поточної роботи.
>
> **Мова:** спілкуйся з власником українською мовою. Усі нові або змінювані користувацькі тексти інтерфейсу, документацію, описи PR, коментарі та звіти пиши українською. Не перейменовуй технічні ідентифікатори, API, назви бібліотек і команди, якщо це не потрібно для завдання. Загальноприйняті технічні назви можуть залишатися англійською. Якщо наявні англомовні тексти поза межами завдання, зафіксуй їх у звіті, а не змінюй самовільно.
>
> На початку перевір поточну гілку, HEAD, стан робочого дерева та незакомічені зміни. Не перезаписуй, не видаляй і не привласнюй чужі зміни. Якщо стан незрозумілий, є конфлікт або ризик втрати роботи — зупинися й повідом власника.
>
> Виконуй лише вказаний етап. Не переходь до наступних етапів, не розширюй обсяг самостійно й не трактуй припущення як погоджені вимоги. Якщо виявиш суперечність, критичний ризик або потребу в змінах поза межами етапу, поясни це та дочекайся рішення власника.
>
> Дотримуйся обмежень поточного коментаря. Не виконуй руйнівних Git-операцій і не змінюй конфігурації, дані чи інші файли поза погодженим обсягом. На етапі аудиту не змінюй жодних файлів.
>

>
> Напиши звіт українською мовою та включи:
>
> - виконаний обсяг і результат;
> - змінені файли (для етапу реалізації) або досліджені файли й компоненти (для аудиту);
> - перевірки та точні результати команд і тестів; окремо зазнач, що не запускалося;
> - відомі ризики, обмеження й невирішені питання;
> - підтвердження стану Git і наявності або відсутності незакомічених змін;
> - перевірку відповідності мовним вимогам;
> - оцінку відповідності критеріям приймання поточного етапу.
>
> Не вигадуй результати перевірок і не стверджуй, що дію виконано, якщо це не перевірено. Не починай наступний етап, не зливай PR і не внось додаткових змін без окремого явного дозволу власника. Після звіту зупинись і дочекайся рішення.

## 5. Шаблон коментаря для етапу

Для кожного нового етапу в Issue використовувати таку структуру:

- **Назва:** «Етап N — коротка назва».
- **Мета:** який результат потрібно отримати.
- **Обсяг робіт:** конкретні завдання.
- **Обмеження:** що заборонено змінювати або виконувати.
- **Мовні вимоги:** нові тексти інтерфейсу, документація, коментарі та звіт — українською мовою.
- **Критерії завершення:** як перевірити, що етап завершено.
- **Формат звіту:** за потреби — один звичайний коментар у відповідній Issue або PR; перший рядок — `Dev-agent`. Reply і посилання на коментар-джерело не обов’язкові.
- **Наступний крок:** не починати без погодження власника.

## 6. Рекомендована послідовність для великих змін

Нижче наведено приклад для Issue #63. Остаточний обсяг і порядок етапів визначає власник після ознайомлення зі звітом аудиту.

1. **Аудит архітектури та планування** — лише читання, жодних змін.
2. **Каркас інтерфейсу** — блок завантаження, перелік матеріалів та адаптивне розташування.
3. **Завантаження й метадані** — завантаження кількох файлів, опис матеріалів і збереження сумісності.
4. **Категорії та порядок** — створення й переміщення матеріалів, згортання категорій, збереження порядку та безпечне видалення категорій.
5. **Дії та видимість** — приватний перегляд, спільна демонстрація, показ і приховування для учнів, редагування та видалення.
6. **Адаптивність і навігація** — мобільні дії, доступність, вилучення зайвих пунктів навігації без порушення учнівських маршрутів.
7. **Регресійна перевірка та PR** — автоматичні тести, ручні перевірки, звіт українською мовою та PR до `clean-main`; без злиття до окремого дозволу.

Після аудиту власник може змінити послідовність або розділити чи об’єднати етапи на основі фактичної архітектури. Не ухвалювати такі рішення самостійно до подання звіту аудиту.

## 7. Правила безпеки й прозорості

- Перед будь-якими змінами зафіксувати початковий стан Git.
- Не використовувати `reset`, `clean`, `stash`, `rebase`, примусовий push або інші потенційно руйнівні операції без окремого явного дозволу.
- Не комітити й не публікувати зміни власника без дотримання погодженого процесу.
- Не видаляти й не перезаписувати навчальні матеріали, метадані, локальні конфігурації або незакомічені зміни.
- Не приховувати невдалі тести. У звіті наводити точну команду та її результат.
- Перед відкриттям PR перевірити diff, відсутність випадкових секретів і локальних даних, відповідність обсягу етапу та мовним вимогам.
- Опис PR, його назву та підсумкові пояснення писати українською мовою. Англійські назви технічних сутностей і conventional commit-повідомлення можна зберігати, якщо цього вимагають правила репозиторію.
- Перевіряти всі зміни проти основного Issue, а не лише короткого коментаря.
