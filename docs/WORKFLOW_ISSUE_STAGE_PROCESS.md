# Процес поетапної роботи над GitHub Issue

Цей документ описує узгоджений процес роботи власника проєкту та Dev-агента над великими задачами LyServer. Мета — зберігати повні вимоги, виконувати роботу контрольованими етапами, мати звіт для кожного етапу й не переходити до наступної роботи без погодження.

## 1. Джерела істини

Для задачі, яка розбивається на етапи, використовуються:

1. **Основний текст GitHub Issue** — повна й актуальна специфікація: функціональні вимоги, обмеження, UX, безпека та критерії приймання. Він не замінюється короткими описами етапів.
2. **Коментарі Issue** — окремі завдання на кожен етап. Кожен коментар містить мету, межі, дії, заборони, формат звіту та критерії завершення.
3. **Відповідь Dev-агента на коментар** — звіт саме про вказаний етап. Звіт має залишатися в гілці відповідей на цей коментар.
4. **Погодження власника** — єдиний дозвіл перейти до наступного етапу, почати реалізацію після аудиту або злити PR.

Якщо між коментарем етапу та основним Issue є суперечність, не ігнорувати її: вказати на неї у звіті та попросити власника уточнити вимогу. Основний Issue визначає загальні вимоги, а коментар — обсяг поточного етапу.

## 2. Робочий цикл

1. Власник готує коментар із чітким номером етапу та конкретними межами.
2. Власник передає Dev-агенту посилання на основний Issue **і на конкретний коментар етапу**.
3. Dev-агент перевіряє поточний Git-стан перед будь-якими діями та виконує лише погоджений етап.
4. Dev-агент публікує структурований звіт відповіддю на вказаний коментар. Якщо звіт не можна опублікувати напряму, він передає власнику текст для публікації.
5. Власник перевіряє результат разом із помічником/рев’юером і явно погоджує наступний етап або повертає задачу на доопрацювання.
6. Наступний етап починається лише після такого погодження. Не вважати мовчання, завершення попереднього етапу чи автоматичну відповідь дозволом продовжувати.
7. Для реалізаційних етапів працювати в окремій гілці, запускати доречні тести й відкривати PR у `clean-main`. **Не зливати PR без окремого підтвердження власника.**

### Чому потрібно посилатися на конкретний коментар

Не використовувати неоднозначне формулювання «виконай останній коментар»: пізніше можуть з’явитися уточнення або коментарі інших учасників. Завжди передавати URL/номер коментаря, який є завданням поточного етапу.

## 3. Універсальний промпт для Dev-агента

Скопіювати цей промпт для кожного етапу, замінивши посилання на Issue і коментар:

> Працюй над репозиторієм `shatVM/LyServer`.
>
> **Основне технічне завдання:** [посилання на GitHub Issue]
>
> **Конкретний етап, який дозволено виконувати зараз:** [посилання на конкретний коментар Issue]
>
> Перед виконанням прочитай повний основний текст Issue, усі вимоги й обмеження, а також конкретний коментар указаного етапу. Основний Issue є повною специфікацією; коментар визначає межі поточної роботи.
>
> На початку перевір поточну гілку, HEAD, стан робочого дерева та незакомічені зміни. Не перезаписуй, не видаляй і не привласнюй чужі зміни. Якщо є конфлікт, незрозумілий стан або ризик втрати роботи — зупинися та повідом власника.
>
> Виконуй лише вказаний етап. Не переходь до наступних етапів, не розширюй обсяг самостійно й не трактуй припущення як погоджені вимоги. Якщо виявиш суперечність, критичний ризик або необхідність змін поза межами етапу — поясни це й дочекайся рішення власника.
>
> Дотримуйся обмежень поточного коментаря. Не виконуй руйнівних Git-операцій і не змінюй конфігурації, дані чи інші файли поза погодженим обсягом. Для етапу аудиту не змінюй узагалі нічого.
>
> Наприкінці опублікуй звіт **відповіддю саме на вказаний коментар етапу**. Звіт має містити:
>
> - виконаний обсяг і результат;
> - змінені файли (для реалізаційного етапу) або досліджені файли/компоненти (для аудиту);
> - перевірки та точні результати команд/тестів; явно вказати, що не запускалося;
> - відомі ризики, обмеження й невирішені питання;
> - підтвердження стану Git та наявності/відсутності незакомічених змін;
> - чи відповідає результат критеріям приймання поточного етапу.
>
> Не вигадуй результати перевірок і не стверджуй, що дія виконана, якщо її не перевірено. Не починай наступний етап, не зливай PR і не внось додаткових змін без окремого явного дозволу власника. Після звіту зупинись і дочекайся рішення.

## 4. Шаблон коментаря етапу

Для кожного нового етапу в Issue використовувати структуру:

- **Назва:** «Етап N — коротка назва».
- **Мета:** що саме потрібно отримати.
- **Обсяг робіт:** конкретні завдання.
- **Обмеження:** що не можна змінювати/виконувати.
- **Критерії завершення:** як перевірити, що етап завершено.
- **Формат звіту:** відповідь у гілці цього коментаря, перелік перевірок і результатів.
- **Наступний крок:** не починати без погодження власника.

## 5. Рекомендована послідовність для великих змін

Приклад послідовності для Issue #63 (остаточний обсяг кожного етапу визначає власник):

1. **Аудит архітектури та планування** — лише читання, жодних змін.
2. **Каркас інтерфейсу** — блок завантаження та перелік матеріалів, адаптивне розташування.
3. **Завантаження та метадані** — кілька файлів, опис, збереження сумісності.
4. **Категорії й порядок** — створення, переміщення, згортання, збереження порядку, безпечне видалення категорії.
5. **Дії й видимість** — приватний перегляд, спільна демонстрація, показ/приховування для учнів, редагування та видалення.
6. **Адаптивність і навігація** — мобільні дії, доступність, вилучення зайвих пунктів навігації без поломки учнівських маршрутів.
7. **Регресійна перевірка та PR** — автоматичні тести, ручні перевірки, звіт і PR у `clean-main`; без злиття до окремого дозволу.

Після аудиту власник може змінити послідовність або розділити/об’єднати етапи, спираючись на фактичну архітектуру. Не вирішувати це самостійно до звіту аудиту.

## 6. Правила безпеки й прозорості

- До будь-яких змін зафіксувати початковий Git-стан.
- Не використовувати `reset`, `clean`, `stash`, `rebase`, примусовий push чи інші потенційно руйнівні операції без окремого явного дозволу.
- Не комітити й не публікувати зміни користувача без погодженого процесу.
- Не видаляти й не перезаписувати навчальні матеріали, метадані, локальні конфігурації або незакомічені зміни.
- Не приховувати невдалі тести. У звіті вказувати точну команду та результат.
- Перед PR перевірити diff, відсутність випадкових секретів/локальних даних і відповідність зміни обсягу етапу.
- Усі зміни мають бути перевірені проти основного Issue, а не лише проти короткого коментаря.
