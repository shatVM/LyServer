# Передача LyServer новому ШІ: стартовий путівник

> Мета: дати новому ШІ-асистенту достатній, перевірний контекст для роботи над LyServer без залежності від попереднього чату. Це інструкція до процесу, а не дозвіл виконувати всі відомі завдання.

## 1. Прочитай у такому порядку

1. `AGENTS.md` — обов'язкові правила для агентів, межі дозволів, безпека й звітність.
2. `PROJECT_CONTEXT.md` — призначення системи та історичний контекст. Дати, локальні стани, гілки, коміти й статуси з нього обов'язково звіряй з актуальним GitHub.
3. `REQUIREMENTS.md` — очікувана поведінка продукту та критерії приймання.
4. `DECISIONS.md` — зафіксовані архітектурні/процесні рішення та відомі невизначеності.
5. `docs/WORKFLOW_ISSUE_STAGE_PROCESS.md` — етапний процес, межі завдання та шаблон роботи з Dev-агентом.
6. Повний текст конкретного GitHub Issue і точний коментар, що дає завдання на поточний етап.
7. Фактичні реалізації та тести у відповідних файлах. README пояснює продукт, але не є доказом, що описана поведінка зараз реалізована чи перевірена.

## 2. Ієрархія джерел і суперечності

- Явна остання вказівка власника визначає поточний дозвіл на дії, але не скасовує вимог безпеки.
- Основний текст Issue містить повні вимоги; коментар конкретного етапу обмежує роботу, дозволені дії й критерії завершення саме цього етапу.
- `AGENTS.md`, `REQUIREMENTS.md` і `DECISIONS.md` задають загальні правила/очікування; код, тести, GitHub і середовище підтверджують фактичний стан.
- Якщо джерела суперечать одне одному, не вгадуй і не приховуй розбіжність. Перевір дату/стан джерел, зафіксуй конкретну суперечність і попроси власника ухвалити рішення, якщо вона впливає на роботу.
- Документи, що містять старі Issue numbers, гілки, коміти, результати агентів або статуси, вважай історичними, доки не перевірив їх заново. Зокрема, `GITHUB_ISSUES.md` — каталог підготовлених текстів/чернеток, а не авторитетна карта актуальних номерів Issues; перевіряй реальні Issues на GitHub.
- Не перетворюй roadmap, список ідей або історичний звіт на дозвіл реалізувати все.

## 3. Ролі та межі повноважень

- **Власник проєкту:** визначає пріоритети, уточнює неоднозначні вимоги, погоджує наступні етапи й остаточно вирішує, чи зливати PR.
- **Tech-lead:** допомагає власнику аналізувати стан, розбивати роботу на малі етапи, формулювати перевірні завдання, перевіряти звіти/PR і вести документацію. Не вигадує схвалення власника.
- **Dev-agent:** виконує лише один конкретний погоджений етап, досліджує код, змінює дозволені файли, запускає доступні перевірки й звітує.
- **Reviewer/QA:** перевіряє відповідність критеріям, дифи, тести, ризики й фактичні результати; не підміняє відсутні докази припущеннями.
- **Dispatcher/автоматизація:** може брати лише завдання, які відповідають явно визначеним правилам готовності. Його запуск сам по собі не є дозволом на розширення завдання або злиття PR.

## 4. Незмінні правила робочого процесу

1. Перед роботою перевір актуальну гілку, HEAD, `git status`, незбережені зміни, останні коміти, Issue/PR та релевантні файли.
2. Не працюй безпосередньо в `clean-main`. Створи окрему гілку від актуального `clean-main`, внеси мінімальні цільові зміни й відкрий PR у `clean-main`.
3. Не зливай PR і не закривай Issue без явного дозволу власника та перевірки критеріїв.
4. Виконуй лише поточний етап. Аудит із позначкою read-only не дозволяє редагувати навіть документацію. Наступний етап — лише після явного погодження власника.
5. Не запускай диспетчер або руйнівні/широкі операції без прямого прохання.
6. Не перезаписуй чужі локальні зміни, матеріали, конфігурації чи дані. Не додавай PIN, токени, секрети, персональні дані або локальні матеріали до Git.
7. Не заявляй про запуск тесту, перевірку браузера, доставку повідомлення, push, PR або злиття без фактичного підтвердження. Розділяй: **перевірено**, **повідомлено власником/агентом**, **не перевірено**.
8. Якщо доступний інструмент не дозволяє виконати потрібну дію, не вдавай, що виконав її; повідом про обмеження та запропонуй найближчий безпечний наступний крок.

## 5. GitHub-коментарі та звіти — обов'язковий протокол

- Кожен новий коментар Tech-lead починай окремим першим рядком `Tech-lead`; кожен коментар Dev-agent — окремим першим рядком `Dev-agent`.
- Завдання передавай конкретним посиланням на Issue і коментар етапу. Не використовуй неоднозначне «виконай останній коментар».
- Підсумковий звіт Dev-agent бажано публікувати **Reply саме на коментар, який містить це завдання**. Якщо Reply технічно недоступний, дозволено окремий коментар верхнього рівня в тій самій Issue/PR одразу після завдання; у ньому має бути посилання на коментар-джерело.
- Цю вимогу повторюй у кожному новому завданні Dev-agent.
- Бажаний варіант — Reply саме на коментар із завданням. Якщо інструмент або інтерфейс технічно не дозволяє відповісти в цій гілці, використовуй резервний варіант: опублікуй окремий коментар верхнього рівня в тій самій Issue або PR одразу після коментаря із завданням. У першому рядку постав `Dev-agent`, а у звіті обов’язково дай посилання на коментар із завданням. Не публікуй дубль, якщо звіт уже є. Це дозволений резервний формат, а не підстава зупиняти звітність.
- Звіт містить: результат, змінені файли, коміти/гілку/PR, точні команди та результати перевірок, що не запускалося, ризики й невирішені питання, стан Git і відповідність критеріям. Після публікації перевір, що звіт справді розміщено у правильній гілці.
- Для PR: перевір базову й робочу гілки, diff, тести/CI та відсутність сторонніх змін. Не вважай відкритий PR або повідомлення агента доказом успішного злиття.

## 6. Інтерактивна взаємодія Tech-lead із власником

Це персональна робоча перевага власника проєкту й обов'язкова інструкція для Tech-lead у розмові:

- Коли потрібно обрати один із кількох варіантів, наступну дію, статус або спосіб продовження, **створюй справжні інтерактивні елементи вибору** (наприклад, radio-group, select, checkbox або кнопки), якщо інтерфейс чату їх підтримує.
- Не проси власника друкувати назву варіанта, номер, команду чи фразу, якщо вибір можна подати інтерактивно.
- Елементи мають реально передавати вибраний варіант і запускати відповідну дію/наступний крок; не показуй декоративні або неактивні кнопки.
- Якщо бракує одного критично важливого факту й інтерактивна форма не виправдана, постав одне коротке пряме запитання.
- Не створюй форму лише тому, що завдання широке. Збирай кілька незалежних параметрів в одній компактній формі лише коли це дійсно спрощує вибір.
- Не затримуй виконання: якщо власник просить зробити роботу й даних достатньо, виконуй її, а не пропонуй йому вручну вводити команди чи готувати текст.
- GitHub Issue/PR-коментарі самі по собі не підтримують інтерактивні елементи чату. Там використовуй чіткі текстові інструкції, критерії та варіанти; інтерактивний вибір власника показуй у самому чаті, де це підтримується.

## Цільове серверне середовище

- Цільова платформа сервера — Microsoft Windows із Node.js.
- Конвертація `.ppt`/`.pptx` у PNG залежить від Windows PowerShell, COM-автоматизації та встановленого Microsoft PowerPoint.
- Linux CI не підтверджує роботу PowerPoint COM-інтеграції. Для неї потрібен окремий тест на цільовому Windows-сервері; не заявляй про успішну інтеграцію лише на підставі Linux-тестів.

## 7. Українська мова та стиль

- Спілкуйся з власником українською. Нові/змінені користувацькі тексти, документацію, завдання, коментарі та звіти пиши українською.
- Не перекладай технічні ідентифікатори, API, команди, назви бібліотек і файлів, якщо це може порушити сумісність.
- Формулюй завдання конкретно: мета, межі, дозволені/заборонені дії, критерії приймання, перевірки, формат і місце звіту, умови зупинки.

## 8. Аудит документації для передачі іншому ШІ

Перед тим як сказати, що репозиторій готовий до передачі іншому ШІ, перевір:

- [ ] У корені є коротка стартова інструкція, що посилається на повні документи без дублювання всіх правил.
- [ ] Ролі, права власника, межі агента, заборона автозлиття й етапне погодження не суперечать одне одному.
- [ ] Інструкція про звіти дозволяє звичайний коментар у відповідній Issue/PR і не вимагає Reply.
- [ ] Поточний стан відокремлено від історичних нотаток; Issue numbers, гілки, коміти, статуси та результати перевірено на GitHub.
- [ ] Чернетки Issues чітко позначені як чернетки, а не актуальна карта завдань.
- [ ] Команди тестування відповідають `package.json` і реально доступним скриптам.
- [ ] Критичні вимоги продукту мають перевірні критерії приймання.
- [ ] Вказані відкриті питання, ризики, неперевірені заяви та фактично не реалізовані функції.
- [ ] Зміни документації перевірені на Markdown-помилки, конфліктні формулювання та невірні посилання.
- [ ] Передача не обіцяє, що будь-який ШІ безпомилково виконає правила: потрібно перевірити, чи конкретний агент прочитав інструкції, а після першого завдання перевірити його поведінку.

## 9. Як завершувати роботу

1. Перевір diff і стан Git; упевнись, що змінені лише дозволені файли.
2. Запусти релевантні перевірки. Якщо вони не запускались, прямо зазнач це.
3. Звір результат з критеріями приймання та основним Issue.
4. Онови `PROJECT_CONTEXT.md`, `DECISIONS.md`, `REQUIREMENTS.md` або інші документи лише там, де змінився підтверджений контекст, довгострокове рішення чи вимога.
5. Якщо етап передбачає зміни реалізації або документації в гілці, створи PR до `clean-main` і чекай на рішення власника. Для read-only аудиту не створюй PR без змін: надай звіт і дочекайся погодження наступного кроку. У фінальному повідомленні дай короткий підсумок і посилання на PR або звіт.

## 10. Обмеження

Навіть якісні інструкції не гарантують, що кожна модель або агент їх автоматично завантажить чи виконає. Підтримка `AGENTS.md` залежить від конкретного інструмента й режиму. На старті нового ШІ попроси його коротко підтвердити, які інструкції він прочитав, але не вважай саме підтвердження доказом дотримання правил. Перевіряй першу дію та звіт фактично.
