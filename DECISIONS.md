## 2026-11-09 — `requireAdmin`: чинна адмін-сесія має пріоритет над полем `pin` у тілі запиту

**Контекст:** власник повідомив про помилку: створення викладача з панелі (`POST /api/teachers/create`, лише cookie сесії адміністратора, без `X-Portal-Pin`) → 403, клієнт показував «Доступ має лише адміністратор (вхід за PORTAL_PIN)». Локальна репродукція: сервер насправді відповідав **403 «Неправильний PIN»**. Причина — `extractPin` читає `pin` із тіла запиту, а тіло містить **новий PIN викладача**, який оцінювався як креденціал адміністратора і перекривав чинну адмін-сесію. Той самий дефект стосувався `POST /api/teachers/set-pin {id, pin}`. Виявлено під час роботи над рев'ю Issue #88; впроваджено ще в Issue #85 (`requireAdmin`), панельні тести його не бачили, бо шлють `X-Portal-Pin`-заголовок (він має пріоритет). Невдалі «панельні» спроби також зараховувалися в лімітери PIN.

**Рішення:**
1. **`requireAdmin` (`src/utils/auth.js`): спочатку сесія.** Чинна сесія з `access === "admin"` повертається одразу й не залежить від того, що лежить у полі `pin` тіла чи заголовку. Гілка перевірки адміністративного PIN збережена для stateless-запитів (заголовок `X-Portal-Pin`, CLI, тести); сесія викладача/учня без admin-PIN → 403, без входу → 401 (поведінка без змін). Наслідок: поле `pin` у тілі деяких адмін-запитів більше не може перекрити адмін-сесію й не потрапляє в лімітатори.
2. **`adminApi` (`public/js/teachers.js`) показує текст сервера для 403.** Раніше будь-який 403 маскувався шаблоном «Доступ має лише адміністратор…», що вводило в оману (причина звернення власника). Тепер для 403 показується `message` із JSON або текст відповіді сервера; шаблон — лише запасний варіант. Для 401 підказка клієнта збережена.

**Наслідки:** змінені `src/utils/auth.js` (requireAdmin), `public/js/teachers.js` (adminApi), `test.js` (+3 перевірки: створення/заміна PIN/видалення із сесією адміністратора без PIN-заголовка), цей запис DECISIONS. Тести: `node --check` — без помилок; репродукція на локальному сервері — create 201, set-pin 200, delete 200 (лише cookie); `npm test` — ALL TESTS PASSED (усі перевірки Issue #85, включно з новими — PASS); `npm run test:browser` — 62 PASS / 0 FAIL. Додатковий прибирання: тестовий запис «Сесійний Репро» із репродукції видалено.

## 2026-11-05 — Персональні облікові записи викладачів, розділ «Викладачі» та випадковий адмін-PIN (Issue #85, Етап 1)

**Контекст:** рішення власника в Issue #85 (коментар 6653554595): надати викладачам персональні 4-значні PIN-облікові записи зі своїм ПІБ і додати адміністративний розділ «Викладачі» (сторінка `/teachers`), не розширюючи Issue #22 і не змінюючи сценаріїв учня. Модель облікових даних Issue #63 збережено: операції керування вимагають реальний PIN у запиті, сесія авторизує лише читання/стан/медіа. Після 05-11-2026 (рішення власника) генерацію випадкового адмін-PIN прибрано й повернуто стандартне значення `2468` — див. запись нижче; пункт 8 — лише для історії.

**Рішення:**
1. **Три рівні доступу.** Адміністратор — вхід за адміністративним `PORTAL_PIN` (повні права + розділ «Викладачі»); викладач — вхід за персональним PIN облікового запису (4 цифри, ПІБ, дозволи `demo`/`materials`); учень — без змін. Право `teachers` належить лише ролі адміністратора і не є дозволом, який можна надати запису викладача.
2. **Атрибуція запитів.** Клієнт надсилає персональний PIN разом з ідентифікатором запису: `X-Portal-Teacher` (заголовок) або `teacherId` (тіло запиту). Без ідентифікатора персональний PIN не авторизує жодної операції (403) — свідомо **без fallback** «PIN сам по собі», щоб неможливо було оминути ліміт запису, надсилаючи невідомий id. Адміністративний `PORTAL_PIN` працює без ідентифікатора, як раніше (сумісність зі старими клієнтами збережено).
3. **Сесії.** Поле `role` лишилося `"teacher"|"student"` (сумісність UI), додано `access: "admin"|"teacher"|"student"`, `teacherId`, `fullName`. Сесія адміністратора має `role="teacher"`, `access="admin"`. PIN у сесію не потрапляє. Вхід (`POST /api/auth/verify`) повертає `{ok, role:"teacher", admin:true}` для адміна або `{ok, role:"teacher", teacherId, fullName}` для викладача.
4. **Хешування.** `scrypt` (N=16384, r=8, p=1, keylen=32) з унікальною сіллю, формат `scrypt$N$r$p$salt$hash`, порівняння через `timingSafeEqual`, без кешу перевірки; реалізація у `src/utils/pinHash.js` (без нових залежностей).
5. **Ліміти спроб.** Три лімітатори: IP (5/15 хв), **за обліковим записом** (3/15 хв, `TEACHER_PIN_MAX_ATTEMPTS`) і **за захищеним відбитком PIN** (5/15 хв, HMAC з серверним секретом лише в пам’яті). Невдалий вхід за персональним PIN без ідентифікатора облікового запису лімітується IP-лімітатором і лімітером відбитка PIN — не дає перебирати 4-значні PIN безмежно, навіть змінюючи IP, і не дає одній помилковій спробі заблокувати всі записи; PIN і його хеш у лімітері не зберігаються. Успішна перевірка скидає усі лічильники; заміна PIN скидає лічильник запису; адміністратор від блокування запису не залежить.
6. **Відкликання сесій викладача** (негайно, на сервері): деактивація, архівація, видалення, заміна PIN, зміна дозволів. Дозволи також перевіряються на кожному запиті — відкликання діє без перезавантаження сторінки.
7. **Зберігання.** `materials/.teachers.json` (поза Git через `.gitignore` для `materials/`), читання «свіжого» файлу на кожен доступ (працює CLI `tools/teachers.js` паралельно із запущеним сервером), запис через tmp-файл + rename, синхронні мутації (однопоточний Node).

8. ~~**Адмін-PIN без змінної середовища — ЗАМІНЕНО** (дивитись блок «2026-11-05 — Адмін-PIN: прибрано генерацію…» нижче). Старий текст: Генерується випадковий 6-значний PIN (`crypto.randomInt(100000, 1000000)`), джерело позначається `portalPinSource` (`env`|`generated`); значення друкується **один раз лише в терміналі сервера** (у CI — взагалі не друкується), у HTTP/браузер/логи GitHub Actions не потрапляє. Значення за замовчуванням `2468` прибрано з конфігурації та README; тести й CI завжди задають `PORTAL_PIN` явно.
9. **Захист розділу.** `/api/teachers*` — `requireAdmin` (401 без входу, 403 для сесії викладача/учня і для запиту з персональним PIN); сторінка `/teachers` — серверна перевірка сесії `access="admin"` (403 іншим). У відповідях і розмітці немає ні PIN, ні хеша; дії з наслідками вимагають `confirm`. Пункт меню `.admin-only` ховається клієнтом — лише як зручність.
10. **CLI і документація.** `tools/teachers.js` (`list`/`create`/`set-pin`; PIN з `TEACHER_PIN` або ввід без еха, ніколи не логується); `docs/TEACHERS_PIN_SETUP.md` — локальна процедура створення першого запису; README/REQUIREMENTS оновлено в тій самій гілці.

**Відомі обмеження:** (a) вхід за персональним PIN через `POST /api/auth/verify` не атрибутується конкретному запису (PIN і є ідентифікатором), тому його лімітують IP-лімітатор і лімітер захищеного відбитка PIN — це свідомий компроміс: атрибуція «всім записам» дала б змогу заблокувати входи всієї школи одним помилковим перебором, а атрибуція за невідомим id — оминати ліміт; (b) персональний PIN, що збігається з `PORTAL_PIN`, розпізнається як адміністративний (перевірка адміна перша) — у інструкції заборонено використовувати збіг; (c) `historicalLinks` поки завжди 0 (у метаданих ще немає полів авторства) — панель показує цей показник для майбутніх зв'язків, архівація за замовчуванням безпечніша за видалення; (d) PIN викладача зберігається в `sessionStorage` клієнта (як і раніше) — захист від використання cookie для POST /api/* (Issue #63) збережено; (e) сесії живуть у пам'яті процесу — перезапуск сервера видаляє їх, облікові записи лишаються.

## 2026-10-25 — Доробка Етапу 5: самостійний перегляд опублікованого, повне прибирання `?pin=`, `Cache-Control: no-store`
**Контекст:** подальше завдання Tech-lead у Issue #63 (коментар 6399943123) після звіту Етапу 5: (1) відновити учневі самостійний перегляд опублікованих матеріалів, не відкриваючи прихованих поза активним показом (каталог має оновлюватися при публікації/приховуванні без перезавантаження сторінки); (2) аудит передавання PIN: клієнт не має класти його в URL/логи/історію, зайве приймання `?pin=` із запиту прибрати; (3) приватні медіа не мають бути публічно кешованими — політика `no-store`; (4) надати повну матрицю «ендпоінт × роль» і результати 9 перевірок у звіті.

**Рішення:**
1. **Каталог учня відкрито, але звужено до опублікованого (частково замінює п. 3 Етапу 5).** Нова допоміжна `auth.catalogIdentity(req) → {role} | null` (замінила `isTeacherReader`; відсутній PIN не рахується спробою лімітатора). `GET /api/files`: викладач (PIN або сесія) → повний список; учень (сесія) → `fileService.getFilesList(false)` — **рівно** опубліковані й готові матеріали, без полів `order`/`conversionStatus`, з `description`/`categoryId`; без входу → 403. `GET /api/categories`: читання для чинної сесії (без входу → 403); викладач → усі категорії; учень → лише категорії, що містять щонайменше один видимий йому матеріал (структура прихованого каталогу не розкривається); у відповіді — тільки `id/name/order/createdAt`.
2. **Медіа: опубліковане відкрите завжди, приховане — лише під час активного показу.** `mediaAccess.canViewMedia`: викладач → усе; інакше `fileService.canAccess(name, false)` **або** `stateService.isCurrentlyDemonstrated(name)`. Сесія обов'язкова (`mediaIdentity` → 401 без входу). Сирий PDF/PPTX для не-викладача — 403 (лише PNG-слайди), тому що саме слайди і є контентом для учня. Старі посилання `?pin=` більше нічого не авторизують (перевіряється тестом: 401 без cookie).
4. **Кешування: `Cache-Control: no-store` для всього захищеного контенту.** Медіа `/files/*` і `/slides/*` (плюс `X-Content-Type-Options: nosniff`, у slideController раніше було `max-age=3600`) та приватні JSON `/api/state`, `/api/files`, `/api/categories`, `/api/slides/info`. Мета — приватний вміст не потрапив у спільний кеш браузера чи проксі локальної мережі.

## 2026-10-25 — Етап 5: серверні сесії входу, політика доступу до HTTP-ендпоінтів за ролями та анулювання входів після перезапуску
**Контекст:** завдання Tech-lead у Issue #63 (коментар 6397214254): (1) аудит усіх HTTP-ендпоінтів — залишити лише необхідні маршрути з **серверним** контролем доступу для викладача та учня (приховування UI — це не контроль доступу): учень має отримувати лише стан активної демонстрації та контент, який йому потрібен (включно з прихованим, що саме демонструється), а не загальний каталог, керування матеріалами чи метадані прихованих файлів поза показом; (2) після перезапуску сервера усі входи викладачів і учнів мають скасовуватися — старі cookie/session id/token не відновлюють доступ, а матеріали, акаунти та налаштування не втрачаються.

**Рішення:**
1. **Вхід — через серверну сесію, одна cookie на обидві ролі.** Новий `src/services/sessionService.js`: сховище сесій у пам'яті (TTL 12 год, ідентифікатор — випадкові 192 біти), методи `create/get/destroy/reset/count`. `utils/auth.js` тепер працює з cookie `ly_session` (HttpOnly, SameSite=Strict, Path=/, `Secure` лише за https): `issueSession(req,res,role,name)` / `readSession(req)` / `clearSession(req,res)` / `requireViewer(req,res)` / `mediaIdentity(req,res)`. Методи: `POST /api/auth/verify {pin}` → сесія викладача; **новий** `POST /api/auth/session {name}` → сесія учня; `POST /api/auth/logout` → `sessionService.destroy` + очищення cookie. Сам PIN у cookie не зберігається (лише випадковий id), операції керування і надалі вимагають справжній PIN у заголовку/тілі. Повторний вхід викладача (той самий PIN) перестворює сесію; вхід учня з тим самим іменем переиспользує чинну сесію, з іншим іменем — створює нову.
2. **Політика доступу після аудиту (жоден маршрут не видалено — усі використовуються клієнтом; «скорочення» = звуження області доступу):**

   - читання каталогу — чинною сесією або PIN (без входу — 403): `GET /api/files`, `GET /api/categories` (для ролі «учень» — лише опубліковані готові матеріали; див. запис «Доробка Етапу 5» вище);
   - медіа `GET /files/:name`, `GET /slides/:name/:page`, `GET /api/slides/info` (раніше: опубліковане — публічно): без входу — 401; викладач — усе; не-викладач — **опубліковане завжди, приховане — лише якщо воно демонструється просто зараз** (`mediaAccess.canViewMedia` → `fileService.canAccess` або `stateService.isCurrentlyDemonstrated`), сирий PDF/PPTX — 403 (учень бачить PNG-слайди);

## 2026-10-24 — Одна сторінка учня з двома режимами демонстрації (заміна «перемикання вкладки»)
**Контекст:** відгук рев'ю Етапу 4 (коментар Tech-lead у Issue #63, 2026-10-24) уточнив узгоджену поведінку учнівської сторінки: учень працює в межах однієї сторінки перегляду, режим визначається за серверним станом демонстрації.

**Рішення:** сторінка «Перегляд матеріалів» — єдина сторінка перегляду учня з двома режимами. Під час активної спільної демонстрації вчитель ховає/вимикає на ній вибір матеріалів, категорії та самостійну навігацію: учень лише синхронізовано спостерігає за показом і не може змінювати матеріал або позицію. Після зупинки показу (новий виклик `POST /api/control { stop: true }` з PIN від вчителя) каталог і особистий перегляд повертаються на тій самій сторінці без перезавантаження. «Демонстрація активна» = непорожній `file` у `GET /api/state`. Посилання «Демонстрація» у навігації приховано для не-викладачів; сама сторінка лишається доступною за прямим URL (без змін).

**Замінює:** рішення від 2026-10-14 «Підтверджений напрям синхронізації» (автоматичне перемикання учнівських клієнтів на вкладку «Демонстрація») — воно не було реалізовано в коді; чинна поведінка тепер описана вище. Відповідь на відкрите питання REQUIREMENTS.md («залишати на демонстрації чи повертати до матеріалів»): учень залишається на тій самій сторінці, каталог стає доступним знову.

**Наслідки:** клієнт `public/js/app.js` опитує `/api/state` на сторінці перегляду (початок/зупинка перемикають режими без перезавантаження); стан скидається лише явною зупинкою вчителя; автотести покривають серверний стан, обмеження дій учня та регресію кешу перевірки PNG.

**Статус:** частково замінено записом від 2026-10-25 «Етап 5…»: у ролі «учень» каталогу більше немає, тому після зупинки показу на тій самій сторінці лишається стан очікування наступної демонстрації (а не повернення особистого перегляду). **Доробкою від 2026-10-25 цю частину відновлено в звуженому вигляді:** після зупинки показу на сторінці «Перегляд матеріалів» без перезавантаження повертається каталог лише опублікованих матеріалів, приховані в ньому не з'являються. Сам механізм опитування `/api/state` і перемикання за серверним станом — чинні.

- **Контекст:** уточнення Tech-lead. `auth.mediaIdentity()` повертав лише `isTeacher`/`teacherId`, тож адміністратор (роль `teacher`, `access: "admin"`, `teacherId: ""`) трактувався як звичайний викладач без власника й отримував 404 на медіа чужих викладачів.
