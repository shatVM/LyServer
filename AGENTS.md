# Інструкції для ШІ-агентів у LyServer

Перед будь-якою роботою:
1. Прочитай цей файл, `PROJECT_CONTEXT.md`, а для функціональних змін — `REQUIREMENTS.md` і `DECISIONS.md`.
2. Перевір актуальний стан репозиторію та конкретні файли. Документація й Issues — орієнтир, але код може вже змінитися.
3. Визнач, що саме просить Issue, і не розширюй завдання без потреби.
4. Якщо інформації бракує або є суперечність між кодом, вимогами та рішеннями, зафіксуй це й постав запитання замість здогадок.

Правила внесення змін:
- Не внось зміни безпосередньо в `clean-main`. Працюй в окремій гілці та пропонуй зміни через Pull Request.
- Виконуй одне конкретне завдання за раз. Великий план або roadmap не є дозволом реалізувати всі його етапи одним проходом.
- Перед змінами досліди наявну реалізацію й повторно використовуй чинні механізми, якщо вони підходять.
- Не заявляй, що тести пройшли, якщо їх фактично не запускав. У звіті вказуй точні команди й результати.
- Не видаляй і не перезаписуй користувацькі матеріали, дані або локальні конфігурації без явної потреби та дозволу.
- Не додавай секрети, PIN-коди, токени, персональні дані або локальні файли з матеріалами до Git.
- Не змінюй вимоги чи архітектурні рішення мовчки. Якщо змінилася довгострокова поведінка, онови відповідний документ у тій самій гілці.
- Не зливай Pull Request автоматично. Остаточне прийняття — за власником проєкту.

Після роботи надай короткий звіт:
- що змінилося та навіщо;
- які файли змінено;
- які перевірки фактично виконано і з яким результатом;
- відомі обмеження, ризики та невиконані пункти;
- посилання на гілку або Pull Request, якщо його створено.

## Робота з GitHub Issues
- Виконуй лише конкретні завдання, явно призначені для виконання. Для автоматичного диспетчера базовий маркер готовності — `ready-for-opencode`.
- Загальні roadmap Issues використовуй як джерело контексту, а не як завдання «реалізувати все».
- Не закривай Issue автоматично, якщо критерії приймання не перевірені або Issue не позначена як тестова задача, яку потрібно закрити після валідації.
- Статуси `in-progress` та `opencode-review` означають відповідно роботу агента та очікування перевірки людиною.

## Важливе обмеження
Ці інструкції не замінюють перевірку актуального коду, CI, Issue та фактичного стану середовища. У разі конфлікту пріоритет мають явні вказівки власника проєкту; суперечність слід повідомити, а не приховувати.
