# Інструкції для ШІ-агентів у LyServer

Перед будь-якою роботою:
1. Прочитай цей файл і `docs/AI_HANDOFF.md` (стартовий путівник для нового ШІ), `PROJECT_CONTEXT.md`, а для функціональних змін — `REQUIREMENTS.md` і `DECISIONS.md`.
2. Перевір актуальний стан репозиторію та конкретні файли. Документація й Issues — орієнтир, але код може вже змінитися.
3. Визнач, що саме просить Issue, і не розширюй завдання без потреби.
4. Якщо інформації бракує або є суперечність між кодом, вимогами та рішеннями, зафіксуй це й постав запитання замість здогадок.

Правила внесення змін:
- Не внось зміни безпосередньо в `clean-main`. Працюй в окремій гілці та пропонуй зміни через Pull Request.
- Виконуй одне конкретне завдання за раз. Великий план або roadmap не є дозволом реалізувати всі його етапи одним проходом.
- Перед змінами досліди наявну реалізацію й повторно використовуй чинні механізми, якщо вони підходять.
- Не заявляй, що тести пройшли, якщо їх фактично не запускав. У звіті вказуй точні команди й результати.
- Не видаляй і не перезаписуй користувацькі матеріали, дані або локальні конфігурації без явної потреби та дозволу.
- Не додавай секрети, PIN-коди, токени, персональні дані або локальні файли з матеріалами до Git.
- Не змінюй вимоги чи архітектурні рішення мовчки. Якщо змінилася довгострокова поведінка, онови відповідний документ у тій самій гілці.
- Не зливай Pull Request автоматично. Остаточне прийняття — за власником проєкту.

Після роботи надай короткий звіт:
- що змінилося та навіщо;
- які файли змінено;
- які перевірки фактично виконано і з яким результатом;
- відомі обмеження, ризики та невиконані пункти;
- посилання на гілку або Pull Request, якщо його створено.

## Робота з GitHub Issues
- Виконуй лише конкретні завдання, явно призначені для виконання. Для автоматичного диспетчера базовий маркер готовності — `ready-for-opencode`.
- Загальні roadmap Issues використовуй як джерело контексту, а не як завдання «реалізувати все».
- Не закривай Issue автоматично, якщо критерії приймання не перевірені або Issue не позначена як тестова задача, яку потрібно закрити після валідації.
- Статуси `in-progress` та `opencode-review` означають відповідно роботу агента та очікування перевірки людиною.

## Обов’язкові правила коментарів і звітів GitHub
- Кожен новий коментар у GitHub Issue або Pull Request починай окремим першим рядком, який дорівнює рівно `Dev-agent` (для Dev-agent) або `Tech-lead` (для Tech-lead). Рядок має бути першим байтовим/текстовим вмістом коментаря: без пробілів, Markdown, заголовка, лапок, двокрапки, привітання чи будь-якого іншого тексту перед ним. Після нього — порожній рядок і основний текст. Це правило обов’язкове для всіх коментарів, включно із завданнями, уточненнями, аудитами, зауваженнями, звітами та повідомленнями про приймання. Якщо формат не можна гарантувати — не публікуй коментар, повідом власника в чаті.
- Звіт Dev-agent завжди публікується **новим звичайним коментарем верхнього рівня** в тій самій Issue/PR. Не використовуй Reply і не відповідай у гілці іншого коментаря; звіт є наступним коментарем у стрічці після виконання завдання.
- Перед початком завдання зафіксуй точне посилання на коментар-джерело. Після завершення перевір, що звіт опубліковано як новий коментар верхнього рівня в тій самій Issue/PR; додай у звіт посилання на коментар-джерело.
- Не використовуй Reply ні за яких обставин у цьому робочому процесі. Якщо звіт не вдається опублікувати звичайним коментарем верхнього рівня, зупинись і повідом власника в чаті; не публікуй коментар з неправильним форматом і не створюй дубль.
- У кожному новому завданні для Dev-агента явно повторюй вимогу: «Після виконання опублікуй звіт окремим звичайним коментарем верхнього рівня в цій Issue. Не використовуй Reply. Перший рядок — рівно `Dev-agent`, без будь-якого тексту перед ним. Додай посилання на коментар із завданням. Не дублюй звіт.»
- У звіті вказуй фактичні зміни, перевірки й точні результати, невиконані пункти та ризики. Не заявляй про дії чи тести, які не були виконані.

## Інтерактивний вибір у розмові з власником
- Якщо власнику потрібно вибрати між варіантами, наступними діями або статусами, у чаті використовуй справжні інтерактивні елементи (radio/select/checkbox/кнопки), коли вони підтримуються.
- Не проси власника вводити назву варіанта, номер, команду або фразу, якщо можна дати інтерактивний вибір. Елемент має передавати вибір і запускати відповідну дію, а не бути декоративним.
- Якщо бракує лише одного критичного факту, постав одне коротке пряме запитання; не створюй форму без потреби. Якщо даних достатньо — виконуй роботу.
- GitHub-коментарі не підтримують інтерактивні елементи чату: у них пиши чіткі текстові інструкції та критерії, а вибір власника показуй у чаті.

## Важливе обмеження
Ці інструкції не замінюють перевірку актуального коду, CI, Issue та фактичного стану середовища. У разі конфлікту пріоритет мають явні вказівки власника проєкту; суперечність слід повідомити, а не приховувати.
